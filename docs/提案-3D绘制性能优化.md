# 提案：建模 App 3D 绘制性能优化方案

- 状态：**已生效**（P0 / P1 已落地并通过探针与基准验收；P2 依据实测暂不采用，见 §5）
- 日期：2026-11-16（实施记录见 §11）
- 适用范围：`js/md-paint.js`、`js/md-texmix.js`、`js/tex-stack.js`、`js/model-desk.js` 的绘画链路，以及 `tools/probe-modeldesk.js` 的绘画断言。不改公共 `.os-win*` / `.desk-app` 样式，不影响其他 App。

> 本文区分「已实现」与「计划目标」。已实现项以当前代码与探针为准；计划项都给出可执行的验收路径。
> 原则：**每一期都要么是纯新增能力，要么是「替换并删除旧路径」**，不允许两套实现长期并存。

## 1. 结论摘要

优化前，画笔链路是「CPU 逐三角射线 + 整张 2048² 画布 + 整张纹理上传 + CPU 整图合成」。P0/P1 落地后：渲染改为按需、笔迹上传改为 bbox、提交改为增量采纳、落盘编码移出同步段。命中仍是 CPU 求交，但在当前面数上限内实测不是瓶颈（见 §5）。

| 瓶颈（优化前） | 现状 | 后果 |
|---|---|---|
| 命中测试 | CPU 逐三角求交（粘面快路径只覆盖「同一张面」） | 实测 48k 三角 hitP95 1.0–1.5ms，帧时无影响；>10 万三角才需要 GPU pick（§5） |
| 纹理上传 | 原为每帧整张 `CanvasTexture`（2048² ≈ 16MB） | 已改为脏块上传，单帧 ≈0.06MB（§11） |
| 合成 | 原为有混合层时每个 rAF 整图重合成；抬笔还会回放层栈 | 已改为增量合成 + 抬笔采纳工作副本，抬笔不再重复叠层（§11） |
| 历史/落盘 | 原为抬笔后主线程 `toDataURL` | 已改为异步编码，同步段约 3ms（§11） |

目标（可量化）：**20 万三角 + 2048² 贴图 + 3 层混合层，连续拖动 p95 帧时 ≤ 16ms（60fps），抬笔到可继续操作的停顿 ≤ 50ms。**
当前在面数上限（50000）附近达成：`frameP95 = 16.8ms`，抬笔同步段 `2.8–3.2ms`；20 万三角要等 P3 放开面数上限后才能测。

## 2. 现状基线与度量

先建基准，再改代码。没有数字的优化等于猜。

新增 `tools/bench-paint.js`（无头，产物只进 `.workbuddy/runs/<runId>/`）：

- 场景 A：默认立方体（12 三角）+ 2048² 工作副本（回归基线）。
- 场景 B：`SphereGeometry(1, 200, 120)` = 48000 三角（本 App `MAX_FACES = 50000` 的上限附近）+ 2048² 底座 + 3 层混合层。**20 万三角要等 P3 的 BIN 格式放开面数上限后才能测**，当前格式测不到。
- 动作：`pointerdown` → 200 个 `pointermove`（16ms 间隔）→ `pointerup`，重复 3 轮。
- 指标（`performance.now()` + 纹理上传统计）：
  - `frameP50 / frameP95 / max`；
  - `hitP50 / hitP95`（单次命中测试耗时，与帧时解耦）；
  - `renderP50 / renderP95`、`flushP50 / flushP95`；
  - `uploadMB`（`bytes = w × h × 4` 实算，区分全量 / 局部）；
  - `composeCount`（混合模块整图重算次数，增量合成不计）；
  - `commitSyncMs`（pointerup 同步段：入栈 / 历史 / 调度）；
  - `commitMs`（抬笔到下一帧可继续绘制的停顿，含等 2 帧的 ~33ms 下限，只作参考）。
- 门槛：场景 A 不退步；场景 B 达到第 1 节的目标值，否则该期不算完成。

> 该 bench 是长期资产，不是一次性脚本：后续每一期都用同一份数据对比，禁止用截图或体感验收。

## 3. 专业软件怎么做的（可借鉴的 6 条原则）

参考对象：Substance 3D Painter、Mari、ArmorPaint、Blender 纹理绘制、Photoshop / Krita 的 2D 画布。

| 原则 | 专业软件的做法 | 对本项目的含义 |
|---|---|---|
| P1 绘制发生在 UV 空间 | 笔刷最终落点是贴图像素；屏幕只负责把笔刷投影到 UV | 现在的 `paintStampUV` 方向是对的，应继续把「屏幕 → UV」做成独立、可替换的一步 |
| P2 命中用 GPU 缓冲 | ArmorPaint / SP 一类工具先渲一张 `uv + depth + normal` 的 pick buffer，笔刷在屏幕空间直接读它得到 UV，无需 CPU 逐三角求交 | 只有面数上限放开到 10 万+ 才会成为结构性瓶颈；当前实测不是（§5），暂不预埋 |
| P3 纹理按 tile 管理 | Mari 的 UDIM、Krita/PS 的 tile（常见 64/128/256）脏块回写 | 只上传笔刷 bbox 覆盖的块，而不是整张 2048²（已用 bbox 中转画布实现，§11） |
| P4 稀疏层 + 缓存合成 | 图层是稀疏像素；合成结果按「层版本号」缓存，未变不重算 | 已按 bbox 增量合成；层参数变化才整图重算 |
| P5 笔刷引擎先行 | PS/Krita 的笔迹 = spline 采样 + 间距 + 图章（含压感/倾角），不是「事件到一个点画一个点」 | 把「采样/间距/图章」与「画布写入」解耦，为压感与平滑留位置（已拆出 `js/paint-stroke.js`） |
| P6 历史是补丁 | 撤销存命令 + 受影响块，不存整图 | 现在存层引用已接近；落盘 PNG 编码已移出主线程（P0） |

> 说明：以上是工程原则层面的归纳，不依赖某个版本的具体实现细节；本项目不引入任何第三方引擎或 npm 依赖。

评分：收益 1–5，成本 1–5（越低越好做），风险 1–5（越低越安全）。

| 编号 | 方向 | 收益 | 成本 | 风险 | 结论 |
|---|---|---|---|---|---|
| D1 | 事件合并 + 粘面快路径 + 对象池（**已做**） | 4 | 1 | 1 | 已落地，保留 |
| D2 | 悬停光圈求交节流（**已废弃**） | 3 | 1 | 1 | 光圈改为固定屏幕尺寸，不再按落点求交，节流逻辑已移除 |
| D3 | 工作副本关 mipmap（**已做**） | 3 | 1 | 1 | 已落地，保留 |
| D4 | 按需渲染：无输入/无脏块时不重绘 | 4 | 2 | 1 | **已实现**（P0） |
| D5 | 抬笔落盘异步化（Idle/Worker 编码） | 3 | 2 | 2 | **已实现**（P0） |
| D6 | 笔刷引擎：UV 空间 spline + 固定间距 + 图章池 | 3 | 2 | 2 | **已实现**（P0，`js/paint-stroke.js`） |
| D7 | 脏矩形合成：只重合成笔刷 bbox | 4 | 3 | 2 | **已实现**（P1） |
| D8 | TileTexture：分块画布 + `texSubImage2D` 脏块上传 | 5 | 4 | 3 | **已实现（变体）**：不做 256² 块，直接按 bbox 中转上传，见 §11 |
| D9 | GPU 预览合成：混合层 + 笔迹进 shader | 4 | 5 | 4 | 不采用（当前规模无收益，见 §5 P2 决策） |
| D10 | GPU pick buffer：屏幕 UV/depth/normal 缓冲取命中 | 5 | 4 | 4 | **不采用（暂缓）**：实测命中不是瓶颈，见 §5 P2 决策 |
| D11 | 分辨率自适应：拖动时半分辨率预览，抬笔合并 | 4 | 3 | 3 | 不采用（D8 变体已达标，不与 D8 并行） |

## 5. 分期计划

### P0：不改架构的确定性收益（1 个提交批次）

| 项 | 改动 | 验收 |
|---|---|---|
| P0-1 | `tools/bench-paint.js`：场景 A/B + p50/p95 + 上传量 + 合成次数 | 能稳定输出 JSON；场景 A 记录基线 |
| P0-2 | 按需渲染：视口 `rAF` 从常驻改为「有输入 / 有脏块 / 有动画时」才请求下一帧 | 静止 2s 内 `renderer.info.render.frame` 不再增长；拖动时仍每帧渲染 |
| P0-3 | 落盘异步：`persistOps` 的 `toDataURL` 移出主线程（优先 `createImageBitmap` + `OffscreenCanvas.convertToBlob`，不可用则 `requestIdleCallback`） | 抬笔后 `commitMs` 下降 ≥ 50%；截图/编码不阻塞拖动 |
| P0-4 | 笔刷引擎收口：把 `move()` 里的插值/间距/图章抽成 `strokeSamples()`（纯函数，可在 Node 里单测） | `tools/md-stroke.js` 纯逻辑单测；行为与现状逐像素一致 |
| P0-5 | 删除 `paintCommitLegacy` 与 `MDPaint` 里所有「没有 TexStack」的兜底分支 | 全仓无引用；探针全绿 |

**P0 完成判据**：bench 场景 B 的 `composeCount` 不增加的前提下，p95 帧时相对基线下降 ≥ 20%；`node tools/test-headless.js modeldesk` 全绿。

> 状态：5 项全部落地（2026-11-16）。实测见 §11。

### P1：脏矩形（关键结构改造）

1. `TexStack` 的 stroke 层增加 `bbox`（图章包围盒并集），回放与合成按 bbox 裁剪。
2. `md-texmix.composeAndApply` 增加「增量路径」：层版本只增不减时，从上一张合成结果出发，只画新增笔迹的 bbox；层被撤销/改参数才整图重算。
3. `md-paint` 每笔记录脏块列表；预览纹理只对脏块调用 `texSubImage2D`。

验收：

- 一笔 120px 笔刷在 2048² 上，单帧上传量 ≤ 1MB（bench 输出）；
- 撤销 / 改混合层透明度后，画面与整图重算逐像素一致（探针做 3 组对照）；
- 有 3 层混合层时 p95 ≤ 16ms。

> 状态：已落地（2026-11-16）。第 3 项没有采用 256² 分块，而是脏块 bbox → 中转画布 → `texSubImage2D`；原因见 §11「canvas 源没有源矩形重载」。

### P2：GPU 投影绘制（根治高模）—— 暂不采用

原计划：pick pass + GPU `HitProvider`，删除 CPU 求交。

**决策（2026-11-16）：暂不采用，保留 CPU 求交。** 依据 `tools/bench-paint.js` 实测：

| 场景 | 三角数 | hitP50 | hitP95 | frameP95 |
|---|---|---|---|---|
| A 立方体 | 12 | 0.0ms | 0.1ms | 16.8ms |
| B 球体（面数上限附近）+ 3 层 | 48000 | 0.6ms | 1.0ms（多次重复 1.0–1.5） | 16.8ms |

命中测试占单帧预算的 6%–9%，帧时没有丢帧（`renderP95` 0.4ms）。GPU pick 需要额外一遍渲染 + 同步 `readPixels`（集显实测量级 1–3ms），属于负收益；8bit UV 编码精度也不足以满足「≤ 1 texel」，要上 MRT/多通道，复杂度和风险都不划算。

重新启用的条件（任一满足）：

1. 面数上限提升到 10 万三角以上（P3 BIN 格式落地）；
2. bench 场景 B 的 `hitP95 > 3ms`，或拖动开始丢帧（`frameP95 > 20ms`）且 `renderP95 < 8ms`；
3. 需要笔刷半径 > 256px 的连续跨面高速拖动。

届时再按原计划执行，并删除 CPU 全网格扫描；当前不预埋任何 GPU pick 代码。

## 6. 接口设计（防止未来出现第二套真源）

当前实际的唯一真源（业务代码不得绕过）：

```text
PaintStroke     纯 UV 空间的采样/插值（tools/md-stroke.js 做 Node 单测）
MDPaint         唯一的指针事件入口 + 工作副本 + CPU 命中（rayHit）
MDPaintUpload   唯一的纹理上传出口：markDirty() / flush() / stats()
md-texmix       唯一的合成入口：composeAndApply() / 增量合成 / adoptPaintCanvas()
TexStack        唯一的层栈：push / undo / rev / ops / bbox
```

- 上传与合成都只在一处发生；事件处理里不再出现第二套「自己贴纹理」的分支。
- `MDPaint` 只依赖 `MDPaintUpload` 的 `markDirty/flush`，不直接摸 renderer 的纹理对象（`md-paint-upload.js` 内部处理）。
- P2 如果重开，再按当时的实测引入 `HitProvider` 接口与工厂；**现在不预埋空抽象**，避免为了「以后可能换实现」多一层间接。
- 所有临时对象走对象池（`_rc/_ndc/_inv` 已开先例），每帧新增分配要能在 code review 里指出归属。

## 7. 技术债条款（硬约束）

1. **替换即删除**：P1 落地时删除整图合成路径；P2 落地时删除 CPU 全网格求交。不允许用「保留着以防万一」的理由留下死代码。
2. **一个真源**：层栈只有 `TexStack`；合成缓存只有 `PreviewComposer`；命中只有 `PaintHitProvider`。
3. **探针同步**：任何替换都要同时更新 `tools/probe-modeldesk.js` 的断言；旧断言不得因为「实现变了」而放宽阈值，只能换成更直接的观测（如上传字节数）。
4. **不做兼容层**：本项目不承诺旧 URL / 旧配置格式并存；确需迁移时写一次性迁移函数并在下一期删除。
5. **文件范围**：新增模块只允许 `js/md-paint-*.js` 或 `js/paint-*.js`，并在 `index.html` 里按依赖顺序引入；不得新增根目录 Markdown / 临时脚本。
6. **每次提交必须写清**：改了什么、bench 数字、跑了哪些测试、删除了哪些旧代码。

## 8. 明确不做

- 不引入 Three.js 之外的 3D 引擎、不引入 npm 包、不依赖固定端口的本地服务。
- 不做「GPU 端笔刷图章 + CPU 端另一套图章」的双实现。

## 11. 实施记录（2026-11-16）

### 11.1 修掉的四个真问题

**（1）局部上传一直没生效：canvas 源没有「源矩形」重载。**

原实现调用 `gl.texSubImage2D(..., canvas, srcX, srcY, w, h)`（12 个参数）。WebGL2 的 12 参重载只对 `ArrayBufferView` 生效；`TexImageSource` 最多 9 个参数，多传会抛 `TypeError`，被 `catch` 当成「驱动不支持」→ 永久退化成整张上传。

修复（`js/md-paint-upload.js`）：脏块先 `drawImage` 拷进一张按 bbox 尺寸复用的中转画布，再用 9 参形式 `texSubImage2D(target, 0, x, flippedY, w, h, RGBA, UNSIGNED_BYTE, scratch)` 上传。`flipY` 按 `H - (y + h)` 换算，像素结果与整张上传逐像素一致。

同时去掉了「非 WebGL2 就禁用局部上传」的前提：9 参形式在 WebGL1 同样合法，只在真正抛错时才退回整张。

**（2）抬笔时笔迹被叠了第二遍。**

没有混合层时，`composeAndApply` 把工作副本 `pc` 当底座交给 `composeOnto`，`composeOnto` 又把层栈里的 stroke 回放一遍。`pc` 里已经包含全部已提交笔迹，于是 60% 不透明度的笔一抬笔就接近 100%（实测同一像素 `(252,9,9)` → `(255,0,0)`）。

修复（`js/md-texmix.js`）：新增 `adoptPaintCanvas()`，把工作副本按「成品」采纳——首次整图、之后只按新增笔迹的 bbox 拷贝到合成画布（保留 mipmap 质量），**不再回放层栈**；上传量同样只覆盖该 bbox。

探针新增断言：抬笔前后合成图逐像素比较，`diffPx === 0`（旧实现有 7 万+ 像素差异）。

**（3）按块上传时「整张源图翻转」→ 黑块 / 乱线。**

`UNPACK_FLIP_Y_WEBGL` 翻转的是**传入的整张源图**，不是我们要传的那一小块。中转画布只增不减：上一笔撑到 48×48，这一笔只有 6×6，`clearRect` + `drawImage` 之后画布下半部分还是旧笔迹；`FLIP_Y` 把整张 48×48 翻过来再取左上 6×6，取到的是「翻转后的旧内容」→ 画笔经过处出现黑块和被拉长的乱线（用户反馈的现象）。

修复（`js/md-paint-upload.js`）：翻转改在 2D 中转画布里做（`translate(0, h)` + `scale(1, -1)` + `drawImage`），上传统一 `UNPACK_FLIP_Y_WEBGL = false`，`y` 仍按 `H - (y + h)` 换算。

连带修掉一个副作用：`flush()` 末尾用 `renderer.resetState()` 清 three 的纹理绑定缓存，而 `resetState()` 会把 three 记录的「当前渲染目标」清成 `null`；调用方若正往 `RenderTarget` 里画，之后的 `render()` 会按画布尺寸设视口，回读出来是一块放大的局部。现在先记住 `getRenderTarget()`，清完缓存再 `setRenderTarget(prev)` 恢复。

探针新增两条断言（`tools/probe-modeldesk.js`）：

- **GPU 侧对齐**：64×64 `CanvasTexture` → 先传 48×48 大脏块、再传 6×6 小脏块，渲染进 64×64 `RenderTarget` 后 `readRenderTargetPixels`，与 2D 画布逐像素比较（容差 8），要求 `bad === 0`。只比 2D 画布永远发现不了这类错位；把上传临时改回旧写法实测 `bad = 2304`（正好是 48×48 那块），确认断言真的抓得住。
- **渲染目标不被改动**：`flush()` 前后 `getRenderTarget()` 必须是同一个 `RenderTarget`。

**（4）UV 岛遮罩只裁了预览画布，成品仍溢出。**

`paintClipBegin` 只给 `p.ctx`（即时预览）加岛剪裁，抬笔进层栈的 `p.inkCtx`（增量图）没裁。预览时看着被裁住了，一抬笔合成 / 下次重放层栈，岛外的溢色就出现在模型上 —— 遮罩「好像失效了」。画笔、橡皮、模糊笔都走这条增量通道，全部受影响。

修复（`js/md-paint.js`）：`paintClipBegin` 对 `p.ctx` 与 `p.inkCtx` 加同一组岛多边形并成对 `save/restore`（`p.clipCtxs`）；`paintClipRelease` 逐个恢复。

探针新增断言「UV 岛遮罩：抬笔进栈的增量层同样被裁，岛外没有笔迹」：笔刷上限只有 180、岛比笔刷大，直接压不出溢色，所以把 `paintState.size` 调到 2600（半径 1300px > 半张贴图），一笔盖满整张图，再用与 App 无关的第二套实现独立算出岛多边形，逐像素查增量层。旧写法实测 `outside = 4045`，修复后 `0`（`inkPx = 2313308` 证明这一笔确实画上了）。用例末尾撤销该笔，不影响后续用例。

### 11.2 数字（同一台机器，headless Edge，3 轮 × 200 次 move）

| 指标 | 修复前（场景 A） | 修复后（场景 A） | 修复后（场景 B，48k 三角 + 3 层） |
|---|---|---|---|
| frameP50 | 66.7ms | 16.7ms | 16.7ms |
| frameP95 | 99.9ms | 16.8ms | 16.8ms |
| frameMax | 433ms | 99.8ms（首帧建纹理） | 149.9ms（首帧建纹理） |
| 上传总量 | 2368MB | 69.3MB | 66.7MB |
| 上传次数（全量/局部） | 148 / 0 | 2 / 598 | 2 / 599 |
| 单帧局部上传 | 0（全量 16MB） | ≈0.06MB | ≈0.06MB |
| commit 同步段（pointerup 内） | — | 2.8ms | 3.2ms |
| commitMs（含等 2 帧 ~33ms 下限） | 473.4ms | 37.7ms | 40.0ms |
| hitP95 | — | 0.1ms | 1.0ms（重复 1.0–1.5ms） |
| composeCount（3 轮合计） | 3 | 3 | 3 |

说明：

- 上传总量里仍有 2 次全量（各 16MB）：第一次建纹理 + 第一笔提交时建合成纹理。之后每次提交按笔迹 bbox 上传（≈0.6MB）。
- `commitMs` 的测量包含 `requestAnimationFrame × 2` 的等待下限（≈33ms）；真正的主线程同步段用 `commitSyncMs` 表示，为 3ms 量级。
- `frameMax` 的大值出现在第 1 轮首帧（纹理创建 + 首笔提交），不在稳态路径上。
- `composeCount` 3 = 每轮提交一次采纳/合成，拖动过程中为 0。
- 同一命令在并发开发、机器有其它负载时会抖动（`commitMs` 37–70ms），因此验收以 `commitSyncMs` + `frameP95` 为准，`commitMs` 只作参考。
