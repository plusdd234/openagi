# 提案集 · 编码 App v0.1

> **性质**：人工代拟的草案，用于校准提案格式、暴露流程堵点。
> **不是**决策 AI 的产出——决策 AI 尚未接入。如实标注，避免把设计稿当成已运转的系统。
>
> 依据：《决策AI-宪法》v1.0、《决策AI-章程》v0.1 第四节提案格式。
> 每张卡缺任一项即不受理。

---

## 零、先分类：六个缺口里只有两个半能进提案池

用户列出的六层缺口，不能一视同仁地"提假设做实验"。分错类会让提案池被琐碎事项淹没。

| 领域 | 性质 | 处理 |
|---|---|---|
| 编辑器内核 | **主观体验**——判定标准是人的手感 | 人决策，不进提案池 |
| 语言智能（LSP） | **能力缺失**——不是效率可优化，是没有 | 直接补，不进提案池 |
| 执行验证（终端） | **能力缺失** | 直接补；补完后的**回灌策略**才进提案池 |
| 上下文工程 | 行为可优化，有客观指标 | **进提案池** |
| 改动审阅 | 行为可优化，有客观指标 | **进提案池** |
| 多仓协作 | 不投 | 不处理 |

判据只有一条：**这件改动的成功能不能被程序化断言？**

不能，就不是决策 AI 该管的。编辑器好不好用、要不要做 Tab 补全，这些是产品判断——把它们塞进提案池，会让"驳回"变成对产品品味的表决，而 AI 没有这个资格。

## 零之一、当前最大的堵点：没有仪表

**编码 App 没有任何轨迹落盘。** `ops-trace.js` 服务的是蓝图流程（`traceTx`/`traceAppend`），
`code-agent.js` 完全没接。现在关掉窗口，这一轮对话、六次工具调用、你点了几次"放弃"，全部消失。

后果很直接：

- 「监督工作 AI 的实际工作」**没有输入**
- 上表里所有"进提案池"的假设，**指标全部算不出来**
- 章程第五节的"双跑对照"无法执行——没有基线可比

所以 H0 不是可选项，它是其余所有实验的前提。**这一节是整份提案集的重点。**

## H0 · 影子轨迹（唯一现在可执行的提案）

```jsonc
{
  "id": "prop-20261112-H0",
  "grade": "constitutional",
  "thesis": "没有轨迹就没有监督；先装仪表，再谈改良。",
  "hypothesis": "因为编码任务的全部决策点都在工具边界，记录工具边界的结构化事件（而非全量对话）就能支撑监督与实验，且插桩自身开销 < 总时长的 5%。",
  "killCriteria": "轨迹体积使单任务超过 200KB，或插桩耗时占比 >5%，或记录内容包含文件全文导致存储压力——任一成立即否决本方案，退化为采样记录。",
  "blastRadius": { "flows": 0, "rules": 0, "flipRate": 0 },
  "change": {
    "target": "trajectory_format",
    "diff": "新增 code/* 轨迹格式：每个任务一条记录，事件粒度 = 工具边界"
  },
  "evidence": { "baseline": { "pass": 0, "total": 0 }, "shadow": { "pass": 0, "total": 0 }, "samples": [] },
  "rollback": "轨迹写入独立 store，关掉开关即停写；已写记录不影响任何渲染逻辑"
}
```

**为什么是 `constitutional`**：它确立一个新的**轨迹格式**，而轨迹格式是 L0 第三样东西
（「格式变了，历史不可比」）。这意味着一旦定下来，以后改它要人批——这是对的，
因为它是后续所有监督的证据基础。**第一个提案就是宪法级的，这不是巧合。**

### 记录什么（按事件，不按 token）

每个任务一条，事件数组：

| 字段 | 说明 |
|---|---|
| `turn` | 第几轮模型请求 |
| `tool` | 工具名 |
| `argsDigest` | 参数摘要（路径 + 字符数，**不存全文**） |
| `resultDigest` | 结果摘要（成功/失败 + 关键数字） |
| `ms` | 耗时 |
| `applied` / `declined` | diff 卡片的人为判定 |

**刻意不记**：模型原文输出、文件全文、用户输入全文。
理由：监督需要的是"它做了什么、结果如何"，不是"它说了什么"。存全文会把存储和隐私同时压垮，而收益接近于零。

### 怎么验

- **完整性**：跑 5 次真实任务，事后检查是否每一次工具调用都有对应事件，事件数与模型返回的 `tool_calls` 数一致
- **开销**：插桩函数自身耗时 / 任务总耗时 < 5%
- **体积**：单任务 < 200KB（用 `blob-store` 的阈值判断，超出则外置 IndexedDB）

### 依赖

无。这是唯一不依赖任何未实现能力的提案，**可以立刻做**。

### 状态：已实现（2026-11-12）

| 项 | 落点 |
|---|---|
| 轨迹模块 | `js/code-trace.js`（独立 store `openagi:code-trace`） |
| 轮次插桩 | `code-agent.send()` → `toolLoopRun.onRound`（借用已有回调，`tool-loop` 零改动） |
| 工具插桩 | `runTool` 外层包装，`finally` 记账，**不改任何返回值** |
| 判定插桩 | `askApply.finish()`，含人的等待时长 |
| 看板 | 编码 App 顶栏「轨迹」→ `docs/code-trace-panel.png` |

**实测（真模型跑一次）**：9 个事件（5 turn / 3 tool），记录 3 条 = 界面 3 次工具调用，完全对齐；
`readsBeforeFirstEdit = 1`；无源码泄露。

**落地时发现一个仪表错误，值得单独记**：`fs_edit` 最初记了 **785ms** ——
那不是工具耗时，是 `askApply` 阻塞等用户点「应用」的时间混了进去。
修正后是 **8ms**，人的 254ms 单独记在 diff 事件的 `wait` 里。
**这类"测到了但测的不是那个东西"是仪表最容易犯的错，而且不会报任何错。**

## H1 · 上下文地图（依赖 H0）

```jsonc
{
  "id": "prop-20261112-H1",
  "grade": "ordinary",
  "thesis": "模型盲读文件，是当前效果与成本的双重瓶颈。",
  "hypothesis": "因为模型不知道文件里有什么，只能逐个 ws_read；若在开局给一份仅含「路径 + 导出符号名 + 行数」的地图（不含内容摘要），会让首次 fs_edit 前的 ws_read 次数中位数下降 ≥30%，且 diffAcceptRate 不下降超过 5pp。",
  "killCriteria": "① 读取次数下降但 diffAcceptRate 下降 ≥10pp（说明它在凭地图猜）；② totalTokens 不降反升（地图本身太贵）；③ 同一任务被重复读取同一文件（说明地图误导了定位）。任一成立即否决。",
  "blastRadius": { "flows": 0, "rules": 1, "flipRate": 0 },
  "change": { "target": "code_agent_prompt", "diff": "SYS_BASE 增加地图注入段 + ws_tree 返回符号信息" },
  "evidence": { "baseline": { "pass": 0, "total": 0 }, "shadow": { "pass": 0, "total": 0 }, "samples": [] },
  "rollback": "提示词段落可开关，关掉即回到纯盲读"
}
```

**预判：这条会部分失败，而且失败的部分最有价值。**

小仓库里地图是纯开销——我上次真机探针，2 个文件的任务只用了 3 次工具调用、19.4 秒，已经很接近最优。给地图只会多花 token。

真正的问题出在大仓库。所以实验必须**按仓库规模分层**：

| 分层 | 文件数 | 预期 |
|---|---|---|
| 小 | < 20 | 地图无收益，甚至有害 |
| 中 | 20–200 | 收益最明显 |
| 大 | > 200 | 地图本身超预算，需要"目录级地图 + 按需展开" |

如果实验证明小仓库有害、只有中仓库有效，正确结论不是"加还是不加"，是**加一个规模阈值**。这种"条件性结论"完全合法，比一个笼统的"有效"更有用。

**关键机制风险**：给摘要会诱发"以为知道就不读了"。所以地图**只给符号名，不给内容摘要**——让它知道"东西在哪"，但必须读才知道"怎么写的"。这个设计选择本身就是假设的一部分。

## H2 · changeset 合并确认（依赖 H0）

```jsonc
{
  "id": "prop-20261112-H2",
  "grade": "ordinary",
  "thesis": "一次一文件一张卡，把审阅成本摊成了点按成本。",
  "hypothesis": "因为改 5 处要点 5 次确认；若合并为一次 changeset 确认，确认次数从 N 降到 1，单任务确认总时长下降 ≥50%，且放弃率上升不超过 10pp。",
  "killCriteria": "放弃率上升 >15pp，或出现「整体放弃后无法只保留其中一项」的场景（即 all-or-nothing 导致有效改动被连带丢弃）——任一成立即否决单一合并形态。",
  "blastRadius": { "flows": 0, "rules": 0, "flipRate": 0 },
  "change": { "target": "code_agent_diff_ui", "diff": "多文件合并为一张 changeset 卡，支持部分勾选" },
  "evidence": { "baseline": { "pass": 0, "total": 0 }, "shadow": { "pass": 0, "total": 0 }, "samples": [] },
  "rollback": "保留单文件模式开关，出问题回到逐卡确认"
}
```

**预判：放弃率会上升超过 10pp。**

原因：人面对 3 个文件的 diff，认知负担不是 3 倍而是更高——他要在脑子里同时权衡三处。而"放弃"是一个比"逐条筛选"便宜得多的动作。

如果这个预判成立，**正确出路不是回退，是两级确认**：

1. 第一级：只列文件列表 + 每个文件的 `+3 -1`，勾选要保留哪些
2. 第二级：只展开被勾选的那些的详细 diff

这样"决策负担"和"审阅负担"被拆开了。原来一张卡的时候，这两个负担是混在一起的——这才是真正的问题。

**新增指标**：`partialApplyRate`（用户只保留部分改动的情况占比）。这个指标能区分"合并有害"和"合并方向对但粒度不对"。

## H3 · 报错回灌策略（依赖「命令执行」+ H0）

**前置：命令执行尚未实现，本提案当前不可执行。** 记录下来是为了让先做命令执行的人知道：命令执行要留出"回灌"的钩子，不要做成只能人看的终端面板。

```jsonc
{
  "id": "prop-20261112-H3",
  "grade": "ordinary",
  "thesis": "回灌全文会浪费 token，但截断可能丢掉关键上下文。",
  "hypothesis": "若只回灌「第一个 error + 前后 10 行 + 错误汇总计数」而非全文，修复轮次不增加，且每次修复的 token 消耗下降 ≥40%。",
  "killCriteria": "① 修复轮次增加 ≥1；② 同一 error 在后续轮复现（repeatErrorRate > 20%），说明截断丢掉了定位信息。任一成立即否决。",
  "blastRadius": { "flows": 0, "rules": 1, "flipRate": 0 },
  "change": { "target": "code_agent_prompt", "diff": "错误回灌裁剪策略" },
  "evidence": { "baseline": { "pass": 0, "total": 0 }, "shadow": { "pass": 0, "total": 0 }, "samples": [] },
  "rollback": "改回全文回灌"
}
```

**`repeatErrorRate` 是这条的核心指标，比 token 更重要。**

「修了报错但没修根因」的表现是：报错消失了一轮，下一轮换个形式又出现。这种情况 token 是省的、轮次甚至没增加，但任务实际上失败了。如果只看轮次和 token，会得到"截断有效"的错误结论。

## H4 · 监督粒度（依赖 H0 + 人工复核）

```jsonc
{
  "id": "prop-20261112-H4",
  "grade": "ordinary",
  "thesis": "监督每步都看等于成本和延迟翻倍，只看结果等于没监督。",
  "hypothesis": "因为决策点都落在工具边界；若在该边界比对「声明意图 / 实际动作 / 结果摘要」三元组，可在跑偏后的下一轮检出，且误报率 ≤15%。",
  "killCriteria": "误报率 >30%——监督变成噪声时人一定会关掉它，此时它的存在价值为负。",
  "blastRadius": { "flows": 0, "rules": 0, "flipRate": 0 },
  "change": { "target": "supervisor_policy", "diff": "监督触发点定义" },
  "evidence": { "baseline": { "pass": 0, "total": 0 }, "shadow": { "pass": 0, "total": 0 }, "samples": [] },
  "rollback": "监督本就是 shadow 模式，关掉只影响记录"
}
```

**为什么放在最后**：它需要 20 次真实任务的 **shadow 记录 + 人工事后复核**才能算误报率。
人工复核是这条提案里最贵的部分，也是唯一无法自动化的部分。

**这一条如实暴露了制度的真实成本**：监督的误报率只能靠人标定。想让它变成"无需人的自运转系统"，在这一步就走不通——但走不通的地方应该写出来，而不是假设它不存在。

## H5 · 反例：一条已经走完全流程的提案

这条**不是待办，是范本**。它已经真实发生过，只是当时没有记录成提案。

| 字段 | 内容 |
|---|---|
| **假设** | 记忆压缩只留 1 轮完整往返，会让编码任务丢掉「我已改完」的认知；改为 `keepRounds: 2` 可让任务自然收尾而不是撞轮次上限 |
| **基线（实测）** | 125 秒 / 8 轮撞上限 / 应用 diff 后又读文件、扫目录、搜索共 7 轮 |
| **改动** | `tool-loop.js` 的 `buildWindow` 保留 2 轮 |
| **结果（实测）** | 20 秒 / 3 次工具调用 / 自然收尾 |
| **killCriteria（当时若写会是什么）** | 若 token 上升 >60%，或不改收敛而只把上限调高，则否决 |
| **结论** | 成立。且**默认值保持 1**，只有编码链路传 2——因为 SVG 链路不需要 |

**这条最有价值的地方是它的基线是真实数字，不是估计。**

「125 秒 → 20 秒」这样的对照，比任何架构讨论都有说服力。提案制度的意义就是把这种偶发的发现，变成可复现的流程。

## 一、执行顺序（按依赖，不按价值）

```
命令执行 ──┐
           ├──→ H3（回灌策略）
H0 影子轨迹 ┼──→ H1（上下文地图）
           ├──→ H2（changeset）
           └──→ H4（监督粒度，还需人工复核）
```

**H0 是唯一入口。** 其余全部被它阻塞，因为它们的指标都要从轨迹里算。

这不是流程设计的问题，是**没有仪表就无法测量**。先做 H1 而不做 H0，会得到一堆"感觉快了"的结论——那种结论不能进章程第五节的"双跑对照"。

## 二、这批提案的预期下场

按章程第五节，**大多数提案应该在「双跑对照」这一步自动作废，不占用人的注意力**。

对这批的预判：

| 提案 | 预判 |
|---|---|
| H0 | 成立（唯一确定性高的一条，因为它是加观测不是改行为） |
| H1 | **部分成立**——小仓库有害，需加规模阈值 |
| H2 | **预判否决**——放弃率上升，需改成两级确认 |
| H3 | 待定，依赖命令执行的质量 |
| H4 | 待定，且可能因人工复核成本过高而搁置 |

如果全部成立，说明这批假设在描述"显然的事"，不是在探索。**有两条应该失败，这是健康的信号。**

## 三、这份文件暴露的两个制度缺口

1. **`evidence.baseline` 现在填不出真数。** 五张卡里全是 `{pass:0,total:0}`。
   章程要求基线必须来自独立执行方，但现在**没有执行方也没有样本**。
   这意味着：在 H0 落地之前，任何提案的 `evidence` 都是空的，按格式应该**被拒收**。
   ——这条如实记录，不粉饰。

2. **`grade` 的分级判断没有实现。** H0 我标了 `constitutional`，理由是它触及轨迹格式。
   但这是人判的，不是 `C12` 算的。章程第三节的四条可计算判据，一条都还没跑起来。
