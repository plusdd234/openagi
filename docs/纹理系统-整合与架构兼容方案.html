建模 App 纹理系统调研
与编辑器整合 / 架构兼容方案

把「纹理混合（md-texmix）」「纹理绘制（md-paint）」「纹理映射（md-uv-editor + seed-uv + 投射烘焙）」三个子系统当成一个整体看： 它们共用同一份 doc.materials.slotMaps，却对这张图有三种互不兼容的定义。本文先给实测证据，再给一套能逐步落地、且不打断现有功能的整合方案。

§0 结论三句话

先说结论，后面每一节都是它的证据与展开。

现状
4 写 / 5 读 挤在一个字段上
绘画、混合烘焙、投射烘焙都在写 slotMaps；材质、烘焙工作区、绘制工作区、UV 编辑器、模型库各有一套「底图」取法。
实测缺陷
同一操作两种结果
同一个「拖岛→烘焙」，slotMaps 为空时把混合层永久烙进基础图（R=128 G=254），非空时又完全不含混合效果（白底 99.4%）。
方案
一个栈 + 两个入口
贴图升级为 base + ops[] 的可重放栈；全工程只保留 resolveTex() 读、commitTex() 写；「烘焙」拆成「应用一层」与「固化为底图」两个动作。
一句话诊断：三个子系统其实都已经写对了自己的那一半，问题在于没有任何一层定义「这个槽的图到底是什么」。 于是每个功能各自回答一次，答案还不一样：绘画说「底图 + 笔迹」，混合说「基础图 + 材质层」，投射烘焙说「视口里那张」—— 最后一个把「视口里那张」写回了 slotMaps，而它不是谁的基础图，它是别人合成的结果。

§2 实测同一个操作，两种结果

探针 tools/_diag-tex-arch.js（两个独立页面，各跑一遍完整链路）。为了能判读，用「白底 + 一层 50% 绿」这种可算的颜色，原画用纯红、落点缩到 5%。

2.1 场景 A：slotMaps 为空（贴图只在材质上 / 导入没写进文档）

步骤观测判读
A1视口模型表面 R/G = 0.748（32867 个采样点）混合层生效
A2__debug().baseMap.from = "live"，512×512烘焙底图 = 视口里那张合成图
A3烘焙后 slotMaps 全图均值 R=128 G=254 B=126（262144 px 全是这个值，白 0%）混合层被烙进了基础图
白 + 50% 绿 = (127,255,127)
A4重建材质后视口 R/G 0.748 → 0.624同一层又叠了一次
方向与「双重」一致

2.2 场景 B：slotMaps 里有真贴图（走 sharedTexture）

步骤观测判读
B1视口 R/G = 0.748（与 A 完全一致）混合层同样生效
B2baseMap.from = "slot"烘焙底图 = slotMaps 原件
B3烘焙后非白像素只有 1594 px（就是那一个红岛），白色 260550 px烘焙结果完全不含混合效果
B4重建后视口 R/G 0.748 → 0.748没有双份
这两张图是同一句用户操作（拖一个岛 → 点烘焙）在两种资产上的结果。 差别不在用户做了什么，只在于 slotMaps[0] 是不是空串。这就是「语义未定义」的具体代价： 它同时造成了「混合层被重复应用」和「烘焙结果不含混合效果」这两个相反的错误，而两个都不会报错。
为什么 A4 只有 0.748→0.624，不是理论上的 0.5→0.25？ 截图取样受环境光/材质本色相乘影响，绝对值不可当标尺（B1 与 A1 数值相同正说明它主要反映「有没有绿」）。 所以本文只把 A3 的像素值当作硬证据（那是从 slotMaps 里直接读出来的），A4 只作方向性佐证； 「第二次叠加」这一步由代码路径确证：md-texmix.js:380 的 baseImg = pc || baked || rec.baseImg， rec.baseImg 就是刚被写绿的那张 slotMaps，而 layers 仍在配置里。

§3 缺陷清单按修复收益排序

等级缺陷症状 / 机理 / 证据
P0-1 「底图」有四个定义 绘画的底 = baked｜混合的底 = slotMaps｜烘焙的底 = baseImg/sharedTexture/live｜UV 编辑器的底 = slotMaps。 同一条链路里换一个资产，同一个按钮的含义就变了（§2 实测）。md-texmix:380 · md-paint:163 · md-proj-bake:1721 · md-uv-editor:593
P0-2 投射烘焙写回「合成结果」 烘焙把「白底 + 混合层 + 岛」整张写回 slotMaps，混合配置里的层没删 → 下次重建再叠一遍。 历史里存的 before 也是合成图 → 撤销会把脏数据固定下来。实测 A3
P0-3 投射烘焙忽略混合层（另一面） 当 slotMaps 有 URL 且 sharedTexture 能解出图时，底图直接取原件，烘焙结果不含混合效果， 用户会以为「烘了没变化」或「烘焙把混合弄丢了」。实测 B3
P1-1 笔迹与 baked 双真源 baked 存在时，绘制工作区以 baked 为底，提交却写 slotMaps。 视口继续显示 baked（compose 里 baked 优先于 slotMaps），笔迹看起来「画完就没了」； 但 GLB 导出带的是 slotMaps —— 所见非所存。md-texmix:380 · md-paint:205
P1-2 分辨率四档互相打架 PAINT_MAX 1024 / MAX_SIDE 2048 / BAKE_MAX 1024 + BAKE_CAP 2048 / 且 live 那张可能是 4096。 每次跨模块流转都重编码一次，细节只减不增：画一笔 → 2048 合成 → 1024 烘焙 → 再合成… 越用越糊。
P1-3 撤销三格式，语义不对等 patch 只回像素不回配置，mix 只回配置不回像素，mats 又是第三套。 一次「烘焙」可能同时改了配置与像素，却只能撤一半。md-history:139-144
P1-4 UV 编辑器只认 slotMaps 贴图只在材质上时显示「无纹理」，用户对着有图的模型调 UV，无从判断对应关系。没有 liveSlotImage 兜底。
P2-1 投射绑定按「岛 id」存 S.binds[islandId] 是内存态且 rebuildUV 直接清空 —— UV 一变（换展开 / 打包 / 盒式投影）所有落位全部丢失， 没有「失效但可重应用」的中间态。
P2-2 入口分散在三处 绘画页签里塞了笔刷卡 + 混合面板（#mdMixBox）；投射烘焙是独立浮动窗口（菜单/命令 projbake）； UV 编辑器又是另一个窗口。三者都要选「当前槽」，各自维护一份 curSlot / S.slot / st.paint.slot。
P2-3 两代引擎并存 texbrush / texpaint / modeltex / svgtex（屏空间笔画 + GPU 投影烘焙，给节点/AI 用）与建模 App 里的这三个模块是**两套世界**： 前者不认 slotMaps，后者不认节点。它们不冲突，但文档/命名上必须划线，否则下次还会有人接错。

§4 目标架构一个栈，两个入口

不新增「第四个子系统」，而是把已有的三者压到同一套契约上：像素只有一份（base），其余的改动都是栈里的操作（ops）。

4.1 核心模型

// 一个材质槽 = 一棵可重放的栈
TexSlot {
  name:  string,
  w, h:  number,
  base:  TexSource,          // 唯一像素底座，有且只有一个
  ops:   TexOp[],            // 有序、非破坏、可开关/可重排
  rev:   number              // 任何 base/ops 改动 +1，用于缓存与「脏」判断
}

// 底座：像素从哪来（不可再拆）
TexSource = { kind:'import', url }          // GLB 抽出 / 用户上传
          | { kind:'asset',  id }           // 资产库（模型库共用）
          | { kind:'flat',   color }        // 槽位色（无贴图）

// 操作：三类，正好对应现有三个子系统
TexOp = { type:'blend',   // ← 纹理混合的「图层」
         img:TexSource, mode, opacity, mask? }
      | { type:'project', // ← 投射烘焙的「绑定」（当前是写回，要改成一层）
         src:TexSource, islands:[{ faces:[i], uvHash, cx, cy, s, op }] }
      | { type:'stroke',  // ← 绘画的「笔迹」（当前是写回，要改成一层）
         canvas }               // 与 base 同尺寸的 RGBA；不落文档，落历史

4.2 两个入口

// ① 读：全工程唯一取图入口。任何人想知道「这个槽现在长什么样」都只调它
resolveTex(slot, purpose) → { canvas, w, h, rev }
//   purpose = 'view'   视口用（按 TexSpec.view 档，带缓存）
//           = 'base'   继续操作时的底（== view，保证「看到的 = 接着改的」）
//           = 'export' 导出 GLB 用（满档位，不缓存）

// ② 写：全工程唯一改图入口。它只接受「栈操作」，不接受一张成品图
commitTex(slot, mutator, label) → entry
//   mutator 形如 (draft) => { draft.ops.push(...) } / { draft.base = ... }
//   内部：改栈 → rev++ → 一帧一次重合成 → applySlotTexture → 记一条历史
这条规则一旦立住，§3 的 P0-1/2/3、P1-1/3 全部自动消失： 底图只有一种定义（resolveTex(slot,'base')）； 投射烘焙不再有机会把合成结果写进 slotMaps（它只能 push 一个 project op）； 绘画与 baked 不再分叉（笔迹也是一层）； 一次操作只产生一条历史（栈的 diff，不含像素，体积从 MB 级降到 KB 级）。

4.3 「烘焙」这个词要拆成两个动作

现在两个面板上各有一个「烘焙」，语义完全不同，用户无从分辨：

按钮现在的行为整合后
投射烘焙 · 烘焙重采样岛 → 写回 slotMaps（破坏性）「应用投射」= push 一个 project op（非破坏，可反复调落位）
纹理混合 · 烘焙合成 → 存成新资产 + 清空 layers（破坏性）「固化为底图」= flatten：把 ops 合成进 base，ops 清空

两者都保留，但措辞与图标区分：应用（加一层，随时可改）vs 固化（烧进底，省内存、便于导出）。这是行业里 Blender「Bake」与「Apply Modifier」的区别，用户学一次就懂。

4.4 渲染与导出契约

  • 材质只认 resolveTex(slot,'view')。makeMaterials 里删掉 MIX.texFor 那条分支，改成问管线；md-texmix 的 texFor/ensureTex/applyBase 全部下沉进管线。
  • 导出 = resolveTex(slot,'export') 的 flatten。GLB 内嵌一张合成好的图，语义与今天一致（导出后混合层「看起来」被固化，但工程里仍可改）。
  • 合成永远在 CPU（2D canvas），不上着色器。理由不变：着色器混出来的只有视口好看，导出是空的（md-texmix.js 头注释已经写明）。
  • 预览走低档：拖动滑杆/拖角点时不重新合成全尺寸，走「低档 resolve + 尺寸不变换」；松手才按 view 档重合成一次。

5.2 与模型库（m3d-slots.js）共用一份配置

两边现在共用 openagi_model_tex_v1，这是对的，别拆。需要补的是「谁写的」与「谁说了算」：

  • 写配置时带 writer: 'modeldesk' | 'library' 与 at；读的时候不校验（兼容旧数据），只在冲突提示里用。
  • 同一槽的 ops 以最后写入者为准（不做字段级合并 —— 合并两个图层栈是伪需求，且会造出谁都没配过的结果）。
  • 模型库暂不实现 project / stroke op：读到未知 op 类型时原样保留、跳过渲染，并在面板上标注「此槽含建模 App 的投射层（N）」。 这样两边版本不必同步升级，也不会互相删数据。

5.3 历史

新增第四种 entry，老的三种继续能撤（不迁移旧历史，只保证读得动）：

// 新：一次操作 = 一条栈 diff，体积与层数成正比，与分辨率无关
{ tex: { key:'默认材质', before:'{"v":4,…}', after:'{"v":4,…}',
        // stroke 这类图层不进行 JSON，改存 canvas 引用 + 尺寸，避免 MB 级字符串
        blobs: { 'op#3': { w:1024, h:1024, url:'data:…' } } },
  label:'应用投射', bytes:… }

// md-history.apply 里保持四个分支：patch / mix / mats / tex
为什么不用「前后两张整图」了：现在一次烘焙 before+after 是两张 PNG dataURL（2048² 轻松 4–6MB）， HISTORY_BUDGET 一撞车就把最老的历史丢掉 —— 用户感觉「撤几步就撤不动了」。 改成栈 diff 之后，一次投射操作 ≈ 几百字节（stroke 层除外，但笔迹本来就需要像素）。

5.4 分辨率：只留三个档位

档位长边用途
TexSpec.view1024视口 / 面板缩略图 / 拖动预览
TexSpec.edit2048绘制、投射采样、导出前合成（= 今天的 PAINT_MAX 与 MAX_SIDE 合并）
TexSpec.exportmin(4096, 源)导出 GLB 时的 flatten，不放大（源多大就多大，永不超源）

规则：底座只缩不放大；一旦某槽的 base 是 2048，后续所有写操作都在 2048 上做，不允许任何模块把它压回 1024（这正是现在「越用越糊」的原因）。

§6 落地三个切片，每个都能单独上线

01

切片一：统一读取（新文件 js/tex-source.js，约 150 行） 已落地

把散在四处的取图逻辑收成一个函数，不改任何写路径，因此几乎零风险：

  • resolveBase(slot) → {img, from}：baseImg → sharedTexture(slotMaps) → baked → liveSlotImage → 槽位色，顺序写死并返回 from（可观测）。
  • 改造点：md-paint.paintEnsureTarget、md-proj-bake.slotBaseImage、md-texmix.baseImageFor、md-uv-editor.uvSyncModelMap 四处改为调用它。
  • 顺带修 P0-1 / P1-4：UV 编辑器终于能看到「只在材质上」的贴图。
  • 这一步就会让 §2 的 A/B 分叉收敛成一个答案（选哪个由 resolveBase 的注释与一次决策固定下来：取 live——所见即所改）。
02

切片二：投射烘焙改「层」，修 P0-2 / P0-3 已落地

  • S.binds 已经是「岛 → 落位」的完整描述，天然就是 project op。落位改成写进栈（内存态即可，先不落 localStorage）。
  • 「烘焙」按钮 = commitTex(slot, d => d.pushOp(projectOp))，不再碰 slotMaps。
  • 另加「固化为底图」= flatten（把 ops 合进 base，写一次 slotMaps，一条历史）。
  • 左栏底图改用 resolveBase，从此「左栏看到的底」与「烘出来的底」由同一个函数保证。
  • 绑定改存 {faces, uvHash}：UV 变了不再静默丢，而是标「失效，点此重应用」（修 P2-1）。

实施中偏离方案的九处（都是踩出来的，不是偏好）

项方案原写法实际落地与原因
resolveBase 顺序 baseImg → slotMaps → baked → live 掉过来了：slotMaps → baked → cached → live。baseImg 是调用方各自的缓存、是最不可信的一档， 排在最后且必须按 url 校验（槽位换图后旧缓存会串味）。
live 兜底 「取 live，所见即所改」 必须排除合成图。混合模块留下的 TB.compose 产物也是挂在材质上的 image，而且它不透明 （已用槽位色打底）；拿它当编辑底座 → 透明信息全丢、每帧还可能变。 判据是比较 image 身份：liveSlotImage 返回 image，MIX.texFor 返回 Texture， 必须先 .image 再比，否则排除逻辑静默失效（实测过：占比 100%）。
新增 adoptLiveBase() 无（方案里没有这一步） 必须补。MIX.applyBase 在 slotMaps 无 URL 时会把材质 map 清成 null， 而那张图正是唯一来源 → 「撤销一下贴图全没了」。两处修：applyBase 见到 live 有图就别清； 打开投射窗时把 live 像素「领养」进 slotMaps，让文档成为真源。
TB.compose 打底色 #ffffff（原实现） 加 baseColor 参数，无底座时用材质槽色 #c9ccd4。白底会让没贴图的模型一进合成就变白， 也会在「只贴了几个岛」的场景把整张贴图污染成 76.5% 白。
导出期 导出时 flatten 写 slotMaps 改成临时换、try/finally 换回（glbTexSwap）。自动保存也走 save()， 固化一次用户就再也没法调落位了。
「固化为底图」的守卫 「没像素就别固化」 判据得是 resolveBase(slot).from === 'slot'。「有没有像素」不够：上一轮的合成图会被 live 兜底取到，用它当底座固化 = 把坏 URL 换成「槽位灰 + 几个岛」，比不固化更糟。
增量画布 无（方案只说「提交 stroke op」） 必须一笔一张，不能复用。复用那张已被推进栈的画布，下一笔的 clearRect 会把上一笔擦掉 （症状：画第二笔时第一笔凭空消失）。落笔时按需分配，抬笔后立刻松手。
混合配置的撤销快照 沿用「JSON.stringify(cfg)」 必须把 ops 摘掉。理由两条：① 语义 —— 混合撤销只该管图层与烘焙图，笔迹有它自己的 tex 条目，混在一起会让「撤销一次滑杆」顺手撤掉十笔；② 性能 —— ops 里是整张 PNG， 拖滑杆时每帧 stringify 一遍直接卡死。snapCfg 只留 {v, layers, baked}。
v4 的体积兜底 无 单条记录序列化后超过 1.2MB 就丢掉 ops 只留图层（退回 v2/v3）。 外置（blob-store）不可用的浏览器里，ops 内联会直接把 localStorage 撑爆， 而 writeStore 的 try/catch 会把它变成「静默不落盘」—— 那比少存一层更糟。
一次性迁移提示 检测「被旧版写脏的 v3」→ 弹「合并 / 忽略」 不做，理由写在 §8：判据无法可靠。「slotMaps 非空 + 配了混合层」在干净模型上同样成立 （导入时就带底图、混合层是在模型库配的），一做就是常态误报；而「合并」本身也无法实现 —— 从合成图里还原不出干净底座。给一句永久误报的弹窗，不如在文档里写清楚：要干净底座就重新导入模型。
仍然遗留的（有意不做，不是忘了）
  • 绑定仍存 island id，未改成 {faces, uvHash} —— P2-1（UV 一改就静默丢绑定）还在。 改格式会动 S.binds 的存档结构，和「一次改一件事」的原则冲突，单独一轮做更稳。
  • v4 的 ops 只跟 textureConfigKey 走：文档还没保存过（没有 key）时不落盘， 此时刷新会丢未导出的笔迹 —— 与「图层只有资产 id 才落盘」的既有语义一致。
  • 模型库不渲染 ops：它只认 layers / baked，所以笔迹不会出现在模型库预览里。 改动前也一样（笔迹当时写在 slotMaps，模型库压根不读），不是新缺口。

§7 性能为什么这套不会更慢

  • 合成次数反而变少：现在「烘焙一次 = 整张重编码 PNG（2048² 约 120ms）+ 材质重建 + 再解码」，改栈之后「应用一层 = push op + 一次合成」，省掉了 toDataURL / Image 解码（这是最贵的两步）。
  • 缓存键：(slot, rev, size, purpose)。rev 不动就直接复用 canvas，不重合成。
  • 合帧：沿用现有 md-texmix.schedule 的 rAF 合并；拖滑杆只跑低档。
  • 内存上界：每槽 1 张 view 档 canvas（1024² RGBA ≈ 4MB）+ 1 张合成画布。10 槽 ≈ 80MB，可接受；project op 不额外持有整图（只持有原画引用）。
  • 导出时才 flatten 到 export 档，用户不导出就不付这份开销。

§8 边界这几件事不做

  • 不做字段级合并：不试图把「模型库的层」和「建模 App 的层」合成一份新栈 —— 只会造出谁都没配过的结果。
  • 不把投射烘焙搬进蓝图节点（与既有的「不要把 ComfyUI 编排搬进蓝图」同一条结论）：节点侧那是 texbrush/texpaint 的另一个世界，两边共享算法（tex-blend）即可，不共享状态。
  • 不引入 WebGL 合成：导出要的是 CPU 上那张真图。
  • 不自动修复被写脏的 v3 数据，也不做「合并 / 忽略」弹窗：判据不可靠（干净模型同样满足「底座非空 + 有混合层」）， 且「合并」本身无法实现 —— 从合成图里还原不出干净底座。要干净底座只能重新导入模型。理由见 §6.2 最后一行。
  • 不做多通道（PBR）：现在只有 baseColor 一张。等真的有 metallic/roughness/normal 需求时，把 TexSlot 换成 Map<channel, TexStack> 即可 —— 本方案的 ops 模型天然支持，不需要再改一次架构。

写探针的一条教训：toHash(canvas) 不要用「缩到 32×32 再算」。 Chromium 在 GPU / CPU backing store 之间切换时，drawImage 缩小的平滑插值会差 ±1， 于是逐像素完全相同的两张图会算出两个哈希 —— 实测表现为「重建前后合成结果不一致」， 而逐像素比对的 diff = 0，查了很久才发现是量具本身在抖。 要么原尺寸抽样，要么直接用带容差的逐点差（mean < 2）。
